## B. New findings from this audit round

### B.1 — [Critical] A3-AUTH lockout-counter suppression is dead code (never wired into AuthScreen)

**Files:** `src/services/CryptoService.ts:722-762`, `src/screens/AuthScreen.tsx:143-167`

CryptoService.ts (the mechanism, added by this week's C1 commit `7bf69ac`):
```ts
* probes inside withAttemptCountSuppressed() and calls registerFailedUnlock() only when
* NONE of the three matched.
*/
private static _suppressAttemptCount = false;
static async withAttemptCountSuppressed<T>(fn: () => Promise<T>): Promise<T> { ... }
static async registerFailedUnlock(): Promise<void> { ... }
```

AuthScreen.tsx (the only place that probes all three credentials — never uses the wrapper above):
```ts
const [panicMatch, realMatch, decoyMatch] = await Promise.all([
  PanicService.verifyPanicPin(entered),
  SecureCryptoService.unlock(entered),
  DecoyVaultService.verifyDecoyPin(entered),
]);
```

**What this means in plain terms:** the whole point of a decoy/panic vault is that entering the
decoy PIN looks indistinguishable from a real login attempt to an observer forcing you to unlock
your phone. But `SecureCryptoService.unlock(entered)` is called directly here, never through
`withAttemptCountSuppressed()`, and `registerFailedUnlock()` has zero callers anywhere in the
repo (confirmed by grep). So every time someone types the decoy or panic PIN, `unlock()` tries
it against the *real* vault's KEK, fails (correctly), and unconditionally increments the real
vault's failed-attempt counter — exactly the bug the C1 commit's own code comment says it fixes.
After 5 such logins, the real vault locks for 5 minutes with a "too many attempts" message,
which (a) tips off an observer that a second, real credential exists, defeating the deniability
guarantee, and (b) locks the legitimate owner out of their own real vault for using their own
decoy vault normally. 100% reproducible, not a race condition or edge case. No test covers this
wiring (the only similarly-named test, `A3Rollback.test.ts`, covers an unrelated rollback-
protection feature).

**Not caused by this session's reconstruction work being wrong** — the mechanism itself is
correctly written; it's simply never connected to its caller. This may be a gap in the original
lost work, not something the recovery introduced (RECOVERY_REPORT.md doesn't claim AuthScreen.tsx
was ever touched by C1's reconstruction, and `git log` confirms C1 never touched that file).

**B.1 resolution status (2026-09-15, Runde 1):** Fixed — `AuthScreen.tsx`'s three-way probe now
runs inside `withAttemptCountSuppressed()`, `registerFailedUnlock()` fires only when all three
fail. `__tests__/A3AuthSuppression.test.ts` (5 tests) proves the actual security property, not
just compilation.

### B.2 — [High] `expo prebuild --clean` regenerated security-relevant files that were never reviewed, not just never restored

**Files:** `android/app/src/main/AndroidManifest.xml`, `android/app/proguard-rules.pro`,
`android/app/src/main/res/`

RECOVERY_REPORT.md documented that F1's `expo prebuild --clean` wiped `MainActivity.kt` and
`android/app/build.gradle`, and that both were restored via `git checkout --` with an empty
`git diff` confirming success. What wasn't checked: **three other files were also wiped, and
they have no prior git history to restore from at all** — `git log --oneline` for each shows
exactly one commit (`046bcbc`, the F1 prebuild itself). There is nothing to diff against; this
isn't a regression from a known-good prior state, it's a first-time, never-reviewed generation.

`AndroidManifest.xml` now contains, traced to exact root causes in `node_modules/`:
```xml
<uses-permission android:name="android.permission.INTERNET"/>
```
— hardcoded unconditionally in `node_modules/@expo/config-plugins/build/plugins/withAndroidBaseMods.js:60-69`
(outside that file's own "OPTIONAL PERMISSIONS, REMOVE WHATEVER YOU DO NOT NEED" comment block),
and independently re-declared by `node_modules/expo-file-system/android/src/main/AndroidManifest.xml:2`
and `node_modules/expo-video/android/src/main/AndroidManifest.xml:2` (Gradle's manifest merger
would add it even if the base template didn't). None of `INTERNET`, `RECORD_AUDIO` (added by
`expo-image-picker`'s config plugin unless explicitly disabled — it isn't), `SYSTEM_ALERT_WINDOW`,
or `VIBRATE` appear in `app.json`'s explicit `android.permissions` list.

**Plain-language impact:** README.md and CRYPTO_PROTOCOL_SPEC.md both describe this app as
"offline, no server, zero-knowledge." No code in `src/` currently makes a network call (verified:
no fetch/XHR/axios/WebView anywhere), so this is latent, not exploited today — but the app now
requests network capability it explicitly claims not to need, contradicting a documented security
property, and enlarging the attack surface for any future dependency compromise.

`proguard-rules.pro` was reduced to 2 generic lines (Reanimated, TurboModule) with no
project-specific rules — see B.3 for why this specifically matters.

**B.2 resolution status (2026-09-15, this round):** `INTERNET` and `SYSTEM_ALERT_WINDOW` are
stripped via `plugins/withStrippedAndroidPermissions.js` (Expo config plugin, survives future
`expo prebuild` runs) and hand-applied to the current `AndroidManifest.xml` pending that
verification. `VIBRATE` is kept — `AutoLockService` uses it for lock haptics. `RECORD_AUDIO` is
kept — confirmed by reading `plugins/withStrippedAndroidPermissions.js`'s `STRIPPED_PERMISSIONS`
list (only `INTERNET`/`SYSTEM_ALERT_WINDOW`) that it was never stripped; this is a deliberate
feature decision, not an oversight: video import with audio is a wanted feature, so the
permission is correctly declared. Full verification that the plugin's manifest output actually
matches the hand-applied file, via a real `expo prebuild` run and `aapt dump permissions` against
a release APK, is deferred to the device-session checklist at the end of this report.

### B.3 — [High] No ProGuard/R8 keep-rules for the native crypto (JNA/lazysodium) bridge; minification is on by default for release

**Files:** `android/app/proguard-rules.pro` (full file), `android/app/build.gradle`

```
-keep class com.swmansion.reanimated.** { *; }
-keep class com.facebook.react.turbomodule.** { *; }
```
That's the entire file. `build.gradle` has `minifyEnabled enableMinifyInReleaseBuilds`, and
`enableMinifyInReleaseBuilds` defaults to `true` if the gradle property isn't set. React Native's
own bundled consumer ProGuard rules (`node_modules/react-native/ReactAndroid/proguard-rules.pro:44`)
keep any class implementing `NativeModule` — since `Argon2Module`, `NativeKeyCustodyModule`,
`RNFileVaultModule`, etc. all extend `ReactContextBaseJavaModule`, the bridge classes themselves
are almost certainly protected automatically. **What is not protected**: the `lazysodium-android`/
JNA layer these modules call into internally. JNA binds native (C) libsodium symbols by reflecting
over a consumer-defined Java interface's method names — if R8 renames those method names (no
`-keep` rule exists for `com.goterl.lazysodium.**` or JNA `Library` interfaces anywhere in this
repo), the binding silently fails at runtime. **Could not be fully verified in this sandbox** —
no network access to inspect whether the `lazysodium-android:5.1.0`/`jna:5.17.0` AARs ship their
own consumer ProGuard rules that would already cover this. If they don't, a release build risks a
silent fallback from native Argon2id/XChaCha20-Poly1305 to the pure-JS paths — the app has those
fallbacks, so it likely wouldn't crash, but it would silently run weaker/non-constant-time crypto
in production with no user-visible signal.

**B.3 resolution status (2026-09-15, Runde 3):** Keep-rules authored — `com.filevault.app.modules.**`,
`com.goterl.lazysodium.**`, `com.sun.jna.**` added to `proguard-rules.pro`. Still **not build-verified**
(no Android SDK in this environment — see the device checklist, Section G): confirm a real
minified release build still runs native Argon2id/XChaCha20 (logcat should show no "JS fallback"
message during a crypto op).

### B.4 — [High] The security spec itself (and README) document a KDF fallback that doesn't exist, and a passphrase floor the code doesn't enforce

**Files:** `CRYPTO_PROTOCOL_SPEC.md:23,58-69`, `README.md:79,193`, `src/services/Argon2idService.ts:56-59`

```
CRYPTO_PROTOCOL_SPEC.md:58-69 (§3.2, "Fallback KDF — PBKDF2-SHA256"):
"Used when the native module is unavailable... Algorithm: PBKDF2-HMAC-SHA256, Iterations: 600 000"
```
Actual code (`Argon2idService.ts:56-59`):
```
// Fallback: @noble/hashes Argon2id (reines JavaScript, läuft unter Hermes...)
// Kein PBKDF2/CryptoJS Fallback - beide Pfade sind echtes Argon2id
```
The real fallback (when native libsodium is unavailable) is a pure-JS **Argon2id**
implementation, not PBKDF2 — stronger than documented, not weaker, but wrong in the one document
whose stated audience is "Cryptographers, security auditors." **README.md carries the identical
error** (lines 79, 193) — meaning this week's own H4 fact-check pass, which verified KDF
parameters against the code, did not catch this specific claim.

Separately, `CRYPTO_PROTOCOL_SPEC.md:533,551` states a "12-char passphrase floor (H4)" sized
against Argon2id-64MiB for the primary lost/stolen-device threat model. The actual vault-creation
minimum, `src/screens/AuthScreen.tsx:265-267,313`, is `const minLen = 8`. The real 12-character
floor exists only for the **backup** passphrase (`src/services/BackupService.ts:31`,
`BACKUP_MIN_PASSPHRASE = 12`). The spec's quantitative brute-force-infeasibility argument for its
stated primary attack scenario is built on a floor 4 characters higher than what that scenario's
actual code path enforces. Cannot tell from the repo alone whether the vault floor regressed from
12→8 at some point, or whether the spec's H4 note simply conflated the two different floors.

Compounding both: `SECURITY.md:3-4` points every vulnerability reporter at
`CRYPTO_PROTOCOL_SPEC.md` as "the security model," with no caveat that the file's own header
(`Version: 1.0`, `Date: 2026-05-22`, "Status: Production-ready after Round 3 fixes") identifies
it as a Round-3-era snapshot, even though later sections (§15.5, the L3 Phase 2b native-custody
addendum) were clearly added afterward and are largely accurate. Nothing in the document signals
which parts are current and which are stale.

**B.4 resolution status (2026-09-15, Runde 4):** Fixed — PBKDF2-fallback claim corrected in both
`CRYPTO_PROTOCOL_SPEC.md` §3.2 and `README.md` to describe the actual @noble/hashes Argon2id
fallback. Passphrase floor: user explicitly asked not to be decided unilaterally
("Sicherheitsentscheidung, keine reine Doku-Korrektur") — asked first, chose "correct the docs to
8 chars," spec and README updated to state the vault (8) and backup (12) floors distinctly. Header
metadata staleness also fixed (see B.11).

### B.5 — [Medium] `BackupService.ts` and `DecoyVaultService.ts` have the same multi-step-keyed-operation-vs-auto-lock exposure that M2 fixed elsewhere, but were not covered by M2

**Files:** `src/services/BackupService.ts` (no `AutoLockService` import anywhere in 378 lines),
`src/services/DecoyVaultService.ts:144-218`

`FileManager.reencryptAll()` and `KeyRotationService`'s rotation methods correctly wrap their
work in `AutoLockService.beginOperation()`/`endOperation()` (per M2). `BackupService.createBackup()`
(loops over every file via `Promise.all`) and `applyBackupData()`/`restoreBackup()` (sequential
`FileManager.importFile`/`NotesService.createNote` per backup entry) do the exact same kind of
multi-step, master-key-keyed work with **zero** such protection:
```ts
for (const f of data.files ?? []) {
  if (!f || typeof f.content !== 'string') continue;
  await FileManager.importFile(f.content, f.type, f.originalName, f.createdAt);   // no beginOperation()
}
```
If auto-lock fires mid-restore, files already processed stay imported but the rest silently
never happen — no per-file result tracking, no resumability (unlike `KeyRotationService`'s WAL),
and `restoreBackup()`'s catch block only logs to console and returns `false`, giving the user no
indication the restore was partial rather than fully failed. `DecoyVaultService.createFakeFiles()`/
`createFakeNotes()` has the same unprotected-loop pattern, at lower practical risk (fixed 3-item
loops, decoy-content handle rather than the real master key).

**B.5 resolution status (2026-09-15, Runde 2):** Fixed — both files now wrap their multi-step
work in `AutoLockService.beginOperation()`/`endOperation()` (`finally`-safe). New test suite
(`B5_BackupDecoyOperationLock.test.ts`, 5 tests) proves `triggerLock()` is actually suppressed
mid-operation and fires again once done, success and error paths both.

### B.6 — [Medium] `restoreMasterWalIfNeeded()`'s `finally` can discard the WAL before a repair attempt has actually succeeded

**File:** `src/services/CryptoService.ts:944-960`

```ts
try {
  ... five field writes ...
} finally {
  await this.deleteItemSecure(this.STORAGE_MASTER_WAL);   // unconditional
}
```
If one of the five repair writes itself throws (e.g. a transient storage error) partway through,
the `finally` still deletes the WAL — the one artifact that would let a later attempt finish the
repair. Requires two failures in a row (the original crash, plus a failure during the repair of
that crash) to actually manifest — narrow, but a real logic gap: the WAL should only be deleted
once every field-write has succeeded, not unconditionally.

**B.6 resolution status (2026-09-15, Runde 3):** Fixed — the WAL is now only deleted after every
field write succeeds (or immediately for a WAL that's unparseable/incomplete and therefore
unrepairable anyway). `B6_B7_WalWipeCompleteness.test.ts` proves a second failure during repair
leaves the WAL in place and a later clean attempt still heals from it.

### B.7 — [Medium] Secure/panic wipe never clears the master-key WAL blob or KDF-meta marker

**Files:** `src/services/CryptoService.ts:1528-1536` (`deleteEncryptionKey`),
`src/services/SecureDeleteService.ts:249-265` (`keysToVerify` list)

`deleteEncryptionKey()` deletes `STORAGE_KEY`/`STORAGE_SALT`/`STORAGE_KEK_SALT`/
`STORAGE_MASTER_ENC`/`STORAGE_MASTER_IV`/`STORAGE_MASTER_MAC`/`STORAGE_BIO_KEK` — never
`filevault_master_wal` or `filevault_kdf_meta`. `SecureDeleteService`'s wipe-verification list
doesn't check for them either. Only exploitable in the brief window between a crash mid-write and
the next unlock (which would normally consume and delete the WAL) — if a panic wipe or manual
secure-delete happens in exactly that window, old wrapped-master key material can survive a
"complete" wipe.

**B.7 resolution status (2026-09-15, Runde 3):** Fixed — `deleteEncryptionKey()` now also deletes
`filevault_master_wal`/`filevault_kdf_meta`; both added to `SecureDeleteService`'s `keysToVerify`
list. `B6_B7_WalWipeCompleteness.test.ts` proves both are gone after `deleteEncryptionKey()` when
a leftover WAL/kdf_meta existed beforehand.
